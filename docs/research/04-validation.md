# План получения проверяемых свидетельств

Все сценарии ниже — **предлагаемые опыты**, не уже пройденные тесты.
Результаты оригинальной платформы в этом шаге не получены. Цель — подготовить
вход для следующего обсуждения и для коллег с доступным стендом.

## Минимальная запись свидетельства

Для каждой проверки хранить:

- ID, вопрос и ссылку на конкретный пункт официального документа;
- авторство/происхождение и условия распространения входного примера;
- исходный текст или маленькую искусственную конфигурацию и её хеш;
- точную сборку платформы, режим совместимости, клиент и язык интерфейса;
- ОС/архитектуру, файловый/серверный режим, СУБД и её версию, локаль и часовой пояс;
- команду или воспроизводимую последовательность действий;
- сырой результат, типы значений, исключения, события и состояние после опыта;
- ожидаемый результат **до** запуска и реально наблюдаемый результат;
- источник наблюдения: `original-1c`, `onescript`, `gonec`, будущий `oddyness`;
- статус: `planned`, `observed`, `reproduced`, `conflicting`, `unsupported`.

Нормализация допустима только для явно несущественных данных: времени запуска,
случайного UUID и путей окружения. Не нормализовать порядок событий, типы,
округление, Null/Неопределено, отказы и откаты — это предмет проверки.

## Как использовать открытый код без самообмана

1. Начать с собственных коротких примеров по документированному контракту.
2. Сравнить несколько парсеров: принятие/отказ и структуру, а не текст JSON AST.
3. Заимствованный тест сохраняет происхождение и лицензию; входные файлы
   внутри открытого проекта могут иметь другие условия, чем код самого runner.
4. Разногласие парсеров превращать в вопрос к оригиналу, не решать голосованием.
5. Ошибочный текст нужен в корпусе наряду с валидным. Для редактора допустимо
   восстановление после ошибки; для запуска нельзя молча исполнить другое дерево.
6. Полноту оценивать по семействам конструкций/режимам, а не числу тестов.

## Проверки для требования «без аллокаций в горячих циклах»

Это будущие **критерии оценки кандидатов**, не результаты текущей работы.

- Сначала определить границу измерения: после разбора/подготовки либо вместе с
  ними; отдельно запуск, прогрев и установившееся исполнение.
- Измерять арифметику на полном требуемом диапазоне, диспетчеризацию вызовов,
  обход коллекций, декодирование строки результата и прокрутку большого списка.
- Для каждого опыта: `ns/op`, `B/op`, `allocs/op`, объём живой памяти, версии
  Go/ОС/CPU, входные данные и escape-analysis на нужном пути.
- В `testing.B`/`AllocsPerRun` не включать подготовку в цикл и не позволять
  компилятору удалить результат. Отдельно проверить редкие пути/переполнение.
- Для UI различать аллокации Go и память native toolkit. «0 allocs/op» в Go не
  означает нулевые выделения в GTK/Qt/AppKit или нулевые копии на границе Wasm.
- Для wazero/wasm2go отдельно измерять создание/компиляцию модуля, вызов host,
  перенос decimal/строк и обработку ошибки. Не складывать всё в одно число.
- Аллокация при создании строки/коллекции может быть частью семантики. Как
  совместить её с требованием горячего пути — вопрос проектирования, а не
  повод изменить пользовательский результат.

В среде исследования `go` не найден в PATH. Поскольку шаг 0 ограничен сбором
информации, toolchain не устанавливался, чужие тесты/бенчмарки не запускались.
Показатели README сторонних проектов не перенесены сюда как наши измерения.

## Задание добровольцу с 1С

Выбрать 3–5 опытов из таблицы, указать сборку/режим, сделать собственную маленькую
конфигурацию без клиентских данных, записать ожидание и фактический результат,
приложить исходники и инструкцию запуска с правами на публикацию. Лучше один
повторяемый контрпример, чем большая база, происхождение которой непонятно.
Скриншоты нужны для UX; значения и события — ещё и в машиночитаемом виде.
