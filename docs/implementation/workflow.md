# Процесс: RUP короткими проверяемыми итерациями

Используем риск-ориентированный итерационный подход RUP: каждое изменение
заканчивается работающим и проверенным результатом. Фазы задают акцент, а не
четыре последовательные очереди «всё спроектировать → всё написать → тестировать».
Требования, проектирование, код и тесты присутствуют в каждой итерации.

- **Inception:** согласовать полезный сценарий, границы и свидетельства приёмки.
  Исследование и текущее архитектурное предложение дают исходную основу.
- **Elaboration:** небольшими исполняемыми срезами снять главные риски:
  точные числа, семантика BSL, транзакции, доступность нативных контролов.
- **Construction:** наращивать полезный складской сценарий, сохраняя рабочий срез.
- **Transition:** проверить установку, восстановление, платформы, ограничения
  и воспроизводимость выпуска. Обнаруженный риск возвращается в обычную итерацию.

## Одна итерация

1. Взять одну готовую по зависимостям карточку [плана](plan.md); прочитать её
   контекст и текущий код. Зафиксировать вход, результат и то, что не входит.
2. Сначала определить проверяемое поведение: пример входа/выхода, негативный
   случай, инвариант. Для исправления — воспроизвести дефект отдельным тестом.
3. Реализовать минимальный вертикальный срез и его тесты в одном изменении.
   Если карточка перестала помещаться в один независимо проверяемый PR,
   разбить её на подкарточки с отдельным результатом до дальнейшего кода.
4. Прогнать короткие проверки. При первой детерминированной ошибке исправить её,
   не запускать дорогую матрицу поверх заведомо сломанной сборки.
5. Затем интеграционные тесты и требуемое «прокликивание». Сохранить лог,
   проверяемый вывод/снимок и точную команду демонстрации.
6. Проверить регрессии, обновить документацию ограничений и строку статуса
   карточки, связать commit/PR и свидетельства. Только после успешных ворот
   текущей ревизии изменение может считаться завершённым.

Атомарность означает одно объяснимое изменение с тестами, пригодное для отдельного
review и отката. Это не разрешение пропускать тесты или превращать одну карточку
в многонедельный мегакоммит. Исследовательская итерация тоже даёт воспроизводимый
результат: исполняемую пробу, измерение и решение, а не только рассуждение.

## Ворота качества

| Уровень | Обязательное свидетельство |
| --- | --- |
| Быстрый | gofmt, сборка без CGO, короткие unit-тесты; ошибки/краевые значения |
| Ядро/БД | Реальная временная SQLite; commit/rollback, повтор операции, перезапуск |
| Формы headless | Команды формы, валидация, состояние, стабильный снимок раскладки |
| Нативный UI | Ввод, фокус, кнопки, открытие/закрытие, проверка сохранённых данных |
| Производительность | Для изменённого горячего участка — benchmem и точный allocation-тест |
| Совместимость | Источник ожидания и версия; неизвестное не обозначается пройденным |

Команды входа создаются в P01 и дополняются по мере появления подсистем:
`go test ./...`, `go test -race ./...` на поддерживаемом runner,
`go test -run '^$' -bench . -benchmem ./...` для измерений. Отдельный тестовый
runner должен разделять быстрые, интеграционные и GUI-задачи; конкретные команды
пишутся в README вместе с реализацией. Сейчас это требования к будущим командам,
а не утверждение об их существовании. Отсутствие Go/дисплея явно записывается
как «не выполнено»; оно не превращает карточку в завершённую.

Нулевые аллокации проверяются после прогрева, на заранее подготовленных данных,
с проверкой результата вычисления. Компиляция, загрузка, форматирование и I/O
измеряются отдельно. Не удалять реальную работу из benchmark ради нуля.
Критические crash/rollback-тесты должны пересоздавать соединение/процесс,
а не только читать буфер той же транзакции.

## Параллельное прокликивание

Долгие независимые сценарии запускаются параллельно с самого появления UI-тестов.
Каждый worker получает свою БД, каталог конфигурации/кэша, процесс приложения,
порты при необходимости и отдельный дисплей или desktop session. Разные тесты
не борются за системный фокус. Для headless возможен `t.Parallel()` после
устранения глобального состояния; нативные UI потоки и главный event loop
подчиняются ограничениям backend, а сценарии распределяются по процессам/runner.

Linux виртуальные дисплеи изолируются на worker. Windows/macOS требуют отдельных
интерактивных сессий/машин, если изоляция в одном сеансе не обеспечена. Внутри
одного сценария действия последовательны. Число worker ограничено ресурсами и
задаётся конфигурацией CI; сначала два независимых сценария должны доказать,
что параллельный запуск не меняет результат. Ожидания привязаны к состоянию
с дедлайном, без произвольных sleep. На ошибке сохраняются снимок, события,
логи и seed. Повтор диагностирует flaky-тест, но не делает красный запуск зелёным.

Headless можно гонять на каждый PR; нативные проверки изменённого backend и
сквозного сценария обязательны до приёмки соответствующей UI-карточки.
Полная Linux/Windows/macOS матрица — перед заявлением о кроссплатформенном выпуске.
Если runner недоступен, статус ограничивается реально проверенной платформой.

## Работа бота и lunobot

Заимствуем практику [lunobot](https://github.com/unxed/lunobot): одна атомарная
часть за рабочий раунд, явные инварианты, проверка актуального SHA, отдельные
изменения общих зависимостей. Конкретный режим PR/staging определяется при
подключении проекта; эта документация сама не регистрирует и не запускает бота.
Технические критерии живут здесь, оперативная очередь/claims — в lunobot.
Если очередь ссылается на Pxx, не копировать туда расходящийся вариант критериев.

Шаблон отчёта для любой модели:

```text
Карточка: Pxx, исходный commit:
Результат пользователя / демонстрация:
Изменено:
Тесты: точные команды, exit code, проверяемые результаты:
UI: сценарии, backend, число worker, артефакты:
Совместимость: подтверждено / предположение / не проверено:
Ограничения и блокеры:
Статус: planned / in-progress / blocked / done; ссылка на свидетельство:
Следующая доступная карточка:
```

Остановиться с воспроизводимым блокером, если нет необходимого источника,
зависимость не поддерживает обязательный контракт или требуется сменить
согласованную архитектуру. Рутинные локальные решения принимать самостоятельно.
Не заменять контракт упрощением молча; обсуждать только конкретную обнаруженную
развилку. Ожидание внешнего контрола не мешает независимой карточке ядра.
