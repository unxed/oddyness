# Сквозная конфигурация «Малый склад»

Предлагаемый первый прикладной пример: учёт расходников мастерской или офиса.
Можно узнать, сколько осталось бумаги, крепежа или кабеля, зарегистрировать
поступление и выдачу. Это проверяет полезную платформенную цепочку без налогов,
стоимости запасов и бухгалтерских счетов. Пока это спецификация, а не готовая
конфигурация, проверенная на оригинальной 1С.

## Граница репозиториев

Конфигурация — отдельный будущий репозиторий; название и публикацию согласуем
при его создании. Платформа не должна знать имён «Товары» или «Поступление».
До появления репозитория допустим минимальный авторский тестовый снимок
`testdata/configs/small-stock` под BSD-3-Clause. После выделения — сохраняем
небольшой снимок с source revision, лицензией и инструкцией обновления; тестам
не нужен доступ к сети. Не ведём две независимо развиваемые копии приложения.
Реальные пользовательские базы не входят в тесты.

[1Ci Jet](https://github.com/1Ci-Company/Jet) полезен как существующий пример
складского приложения, но его полное воспроизведение значительно шире первой
цели. Не делаем его обязательным для первого запуска и не копируем наугад
обработчики. Сначала свой небольшой пример с ясными правами на тестовые данные.

## Минимальная модель

| Объект | Данные / поведение |
| --- | --- |
| Справочник «Товары» | Ссылка, уникальный код, наименование, единица измерения; удаление используемого товара запрещено |
| Документ «Поступление» | Номер, дата, комментарий, строки: товар и количество |
| Документ «Выдача» | Те же поля; получатель — простой текст, без нового справочника |
| Регистр накопления «Запасы» | Измерение: товар; ресурс: количество; регистратор и номер строки движения |
| Отчёт «Остатки» | Товар, единица и точный текущий остаток; фильтр по товару |

Один склад подразумевается контекстом приложения. Нет цен, валют, партий,
резервирования, налогов, печатных форм, сети и сумм по несопоставимым единицам.
Количество положительное, максимум три знака после запятой; лишние знаки
отклоняются, а не молча округляются. Общая числовая модель платформы шире.
Номер документа в первом профиле вводится пользователем, уникальность проверяется
внутри вида документа. Строки одного товара суммируются при проверке остатка.
Непроведённый документ не влияет на запас. Редактировать проведённый документ
можно только после отмены проведения. Удаление проведённого документа запрещено.

Поступление создаёт положительные движения, выдача — отрицательные. Запрет
отрицательного остатка — прикладное правило BSL, исполняемое через транзакционный
API ядра. Отмена поступления также запрещена, если вызовет отрицательный остаток.
Первый отчёт показывает текущий остаток: исторический расчёт «на дату», очередность
задних чисел и восстановление последовательности явно не поддерживаются.

## Сценарии приёмки

Каждый сценарий получает отдельную временную базу. Данные фиксированы; даты и ID
задаются тестом. Проверяем состояние через независимый API чтения/отчёт, а не
только наличие сообщения «Успешно». UI использует стабильные идентификаторы
контролов; координатные клики не должны быть единственным способом адресации.

| ID | Действия | Проверяемый результат |
| --- | --- | --- |
| S01 | Создать «Кабель», единица «м»; закрыть и открыть приложение | Один товар, сохранены код, имя и единица |
| S02 | Создать поступление 10,500, сохранить; затем провести | До проведения 0; после 10,500; статус сохранён |
| S03 | Выдать 2,250 | Остаток 8,250; после перезапуска тот же результат |
| S04 | Попытаться выдать 9,000 | Ошибка; остаток 8,250; документ не проведён; новых движений нет |
| S05 | Повторно провести прежнее поступление | Остаток остаётся 8,250; движения не дублируются |
| S06 | Отменить выдачу; снова провести её | Последовательно 10,500 и 8,250 |
| S07 | Отменить поступление после выдачи | Отказ; статус и движения обоих документов неизменны |
| S08 | Вставить ошибку обработчика после подготовки первого движения | Ноль частичных записей; повтор после исправления успешен |
| S09 | Ввести 0, отрицательное, лишнюю дробную цифру, пустой товар | Каждая ошибка понятна; данные не испорчены |
| S10 | В выдаче две строки одного товара 5,000 + 4,000 при остатке 8,250 | Отказ всей операции, а не частичное проведение |
| S11 | Открыть под ролью чтения и вызвать запись также напрямую через API | Запрет в обоих случаях; отчёт доступен |
| S12 | Попытаться удалить используемый товар или изменить проведённый документ | Отказ; ссылки, документ и остаток сохранены |

S02–S08 — последовательности внутри каждого изолированного сценария; их шаги
нельзя распараллелить. Независимые сценарии и платформенные backend-задачи можно.
Первый практически полезный результат — S01–S07, S09–S10, S12 через GUI и
устойчивое хранение. Для выпуска также обязательны S08, S11, восстановление
из резервной копии и весь набор критериев финальной карточки плана.

Эти тесты фиксируют наше прикладное поведение. Отдельные короткие BSL-пробы из
[исследовательской матрицы](../research/04-validation.md) проверяют совпадение
платформенной семантики с конкретной версией оригинала, когда стенд доступен.
