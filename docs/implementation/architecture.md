# Принятая архитектура

Статус: направление согласовано инициатором; реализация ещё не начата.
Этот документ фиксирует предложение после исследования, а не описание готового
продукта. Конкретные интерфейсы уточняются в небольших итерациях [плана](plan.md).

## Как это работает

Пользователь открывает текстовую конфигурацию. Платформа читает описания
справочников, документов, регистров и форм, проверяет ссылки между ними,
компилирует поддерживаемый BSL и открывает приложение. Из одного описания объекта
получаются структура хранения, программный доступ, список и карточка.
Конфигуратор впоследствии редактирует те же файлы, которые можно менять в Git.
Первый выпуск обходится текстовым редактированием и сгенерированными формами.

Начинаем с одного настольного приложения и локальной SQLite. Внутри разделяем
ядро, исполнение языка, хранение и представление. Ядро можно вызвать без GUI:
это позволяет боту проверять поведение и воспроизводить ошибки автоматически.
Позже те же операции можно вынести за сетевой протокол; сейчас сервер и сетевой
протокол не реализуем.

## Границы модулей

Пути ниже — предлагаемые места для нового кода, не существующие пакеты.
Не создавать заранее пустую иерархию: пакет появляется с первым потребителем.

| Место | Ответственность | Не должно делать |
| --- | --- | --- |
| `cmd/oddyness` | CLI и запуск GUI, сборка зависимостей | Содержать прикладное поведение |
| `internal/metadata` | Версионированная текстовая модель, проверка ID и типов | Открывать базу или окна |
| `internal/value` | Типизированные значения, точные числа, ссылки | Зависеть от SQL/GUI |
| `internal/bsl` | Разбор, разрешение имён, компиляция, VM | Напрямую писать в БД |
| `internal/platform` | Объекты, права, транзакции, проведение, доступные BSL операции | Знать конкретные виджеты |
| `internal/query` | Поддерживаемый запрос → проверенное промежуточное представление | Пропускать произвольный SQL из конфигурации |
| `internal/storage/sqlite` | Хранение, SQL-трансляция, транзакции | Определять семантику BSL |
| `internal/forms` | Состояние и команды форм, ошибки валидации | Дублировать правила ядра |

Ядро получает конкретный контекст операции: пользователь, конфигурация,
транзакция и отмена. Интерфейсы вводим на проверенных границах, без общего
«фреймворка плагинов» и сети микросервисов. GUI и CLI вызывают одни операции.

## Конфигурация и совместимость

Первый собственный формат: каталог с версионированным JSON метаданных и файлами
BSL UTF-8. Стабильные ID не зависят от отображаемых имён. Загрузка атомарна:
невалидная конфигурация не меняет действующую модель или базу. Неизвестные поля,
версии и конструкции отклоняются с путём/строкой и понятной причиной.

Собственный формат не выдаётся за XML/EDT/cf 1С. Импорт этих форматов — будущий
адаптер. Метаданные прикладных конфигураций развиваются отдельно; внутри платформы
допустимы маленькие лицензированные тестовые снимки с указанием происхождения.

Целимся в явно перечисляемую часть поведения 1С 8.x. Каждую возможность отмечаем:
поддержана и проверена, реализована без проверки оригиналом, не поддержана.
Версия оригинала и режим совместимости записываются рядом со свидетельством.
Руководство 8.3.27 — начальная документальная опора, не утверждение о запуске
этой версии. Полная совместимость с типовыми конфигурациями не цель первого выпуска.

## Язык и значения

BSL компилируется в компактный байткод и выполняется небольшой VM на Go.
Парсер LazarenkoA — MIT-кандидат для адаптации, а не готовый язык: сохраняем
числовые лексемы без float64, не игнорируем директивы и неподдерживаемые конструкции.
Goнец изучаем для отдельных механизмов после проверки семантики и лицензий.
OneScript полезен как дополнительный источник примеров и внешняя точка сравнения;
он не является обязательным рантаймом и не заменяет проверку оригинала.

Имена разрешаются при компиляции, локальные значения хранятся в слотах, буферы
переиспользуются в рамках исполнения. Никакого unsafe ради недоказанного выигрыша.
Цель — ноль выделений памяти в определённых прогретых горячих циклах; отдельно
измеряем загрузку, компиляцию, строки, SQL и GUI. Общего обещания «всё без аллокаций» нет.

Числа десятичные, точные. До выбора представления проверяем диапазон, округление,
переполнение и кандидатов по исследовательским NUM-тестам. 19 цифр недостаточно
для заявлений о полном числе 1С; числовой контракт остаётся ранним риском.
SQLite REAL и промежуточный float64 для точных величин запрещены. Кодирование
в БД, сравнение, сортировка и SUM должны сохранять числовую семантику: текстовое
хранение само по себе этого не обеспечивает.

Wasm/wazero оставляем возможностью для конкретного полезного компонента.
Он не является основой BSL в первой версии; wasm2go не считаем средством изоляции.

## Данные, проведение и запросы

SQLite-драйвер без CGO — исходный кандидат (modernc.org/sqlite с проверкой
лицензий зависимостей). На первом этапе одна локальная сессия; второй экземпляр
не должен незаметно обходить это ограничение. Транзакции обязательны даже здесь.
PostgreSQL и несколько пользователей требуют отдельной проверки изоляции,
блокировок, дедлоков и повторов; замена SQL-драйвера недостаточна.

Проведение документа — одна операция ядра: проверить право, прочитать документ,
выполнить BSL-обработчик, проверить движения, заменить старые движения новыми,
пометить документ проведённым и зафиксировать всё одной транзакцией. Любая ошибка
откатывает все изменения. Повторное проведение не удваивает остаток. Отмена
проведения удаляет движения и статус также атомарно. Проверки отрицательного
остатка выполняются внутри той же транзакции, а не по показанию формы.

Запросы разбираются и типизируются до SQL. Первоначально поддерживается только
подмножество, нужное складскому сценарию. Параметры передаются отдельно от SQL;
имена таблиц выводятся из проверенных метаданных. Виртуальная таблица остатков —
операция платформы над движениями, не просто таблица, которую может менять GUI.
Ранний отчёт об остатках использует API ядра; позже тот же результат проверяет
реализацию языка запросов. Это позволяет не блокировать первые демонстрации
полным языком запросов.

## Интерфейс и переиспользование

goWidgets отвечает за нативные окна, раскладку, события и общие контролы.
Формы платформы хранят состояние отдельно от окна, поэтому их можно проверять
без дисплея. Реальное «прокликивание» backend тоже обязательно: headless-тест
не обнаружит все ошибки фокуса, ввода и связывания событий.

В lunobot уже описано развитие Table для zipgui: прежде чем писать таблицу,
проверяем актуальный статус и координируем общий компонент. План не означает,
что Table уже существует. Недостающие Table/редактирование/виртуализация добавляются
отдельными атомарными изменениями в goWidgets. Временный список и отдельная
карточка позволяют начать платформу без ожидания богатой таблицы.

Повторно используем goWidgets и его практики раскладки, реактивности и headless
проверок, не копируем vtui или ZIP-приложение в бизнес-ядро. lunobot задаёт
практику малых проверяемых изменений и отдельного учёта задач. Потребность в
каждой дополнительной библиотеке подтверждаем конкретной карточкой и лицензией.
